# Receive Stream Messages

## Feature overview

EasyIM supports receiving stream messages in one-to-one chats and group chats. A stream message is a real-time transmission mechanism in which content is generated, sent, and received incrementally. It is suitable for scenarios that output long text in segments, such as AI conversations, real-time collaborative writing, and displays of incrementally generated content.

Stream messages are generated by your app server and sent through the [RESTful API](/document/server-side/message_stream_send_single.html). The Web SDK receives, orders, merges, and delivers callbacks for them, but does not allow the client to actively send stream messages.

## Core concepts

Before continuing, familiarize yourself with the following core concepts:

- **Stream message**: A message transmission method that splits a complete message into multiple chunks, which are sent and received incrementally in order.
- **Message chunk**: An individual data segment in a stream message. Multiple chunks form a complete message when combined in order.
- **Current chunk content**: The content of the individual chunk received in the current callback. Retrieve it through `message.stream.deltaText`.
- **Cumulative merged content**: The complete content merged from the first chunk through the current chunk. Retrieve it through `message.stream.fullText`. In the current SDK callback message body, `message.body.content` provides the same content.
- **Stream message transmission state**: An identifier for the transmission phase of a stream message, such as started, in progress, completed, or ended with an error. Retrieve it through `message.stream.status`.
- **Finish reason code**: A business reason identifier provided when a stream message ends. Retrieve it through `message.stream.finishReason`.
- **Message ID**: The unique identifier of a stream message. In the Web SDK, we recommend using `message.msgServerId` to identify the complete stream message. If your app requires a local fallback, you can also use `message.msgLocalId`.

## Supported scope and limitations

- Conversation types: Only one-to-one chats and group chats are supported. Chat rooms are not supported.
- Message types: Only text stream messages are supported.
- Sending method: Stream messages can be sent only through the [server-side RESTful API](/document/server-side/message_stream_send_single.html).
- Client capabilities: The Web SDK supports only receiving stream messages, not sending them.
- Message identifier: `message.msgServerId` identifies the complete stream message.
- Message limitations: For limits on total message length, chunk sending interval, total transmission duration, and other values, see the [server-side API documentation](/document/server-side/message_stream_send_single.html#supported-scope-and-limitations).

## Prerequisite

Before you begin, ensure that the following requirements are met:

- You have initialized the SDK. For details, see [Initialization](initialization.html).
- You registered `ChatManager` during SDK initialization and can monitor stream message events through `client.chatManager.addEventHandler`.
- You understand the EasyIM [limitations](/product/limitation.html).

## Understand the tech

Stream messages are generated by your app server and delivered in chunks to the client SDK through the EasyIM server. The Web SDK triggers the `onStreamMessage` callback as chunks arrive and automatically merges their content in chunk order. Use the current chunk information, cumulative merged content, and transmission state to update the UI in real time until the complete message finishes or ends with an error.

## Integration process and examples

### Integration process

The basic process for receiving stream messages is as follows:

1. After SDK initialization, call `client.chatManager.addEventHandler` to register a message listener.
2. Monitor the stream message callback `onStreamMessage`. When a new chunk arrives, the SDK processes it in sequence-number order before triggering this callback. Out-of-order chunks are temporarily stored until they can be processed. Duplicate chunks and subsequent chunks for a completed message are ignored.
3. In the callback, use `message.msgServerId` to locate the same stream message.
4. Retrieve current chunk information through `message.stream`.
5. In the `onStreamMessage` callback, retrieve the cumulative content merged from the first dispatched chunk through the current chunk from `message.stream.fullText` or `message.body.content`.
6. Update the UI based on `message.stream.status` and stop rendering the stream message when it completes or ends with an error.

### Example code

The following example registers a message listener and receives stream message chunks.

```typescript
client.chatManager.addEventHandler('stream-message', {
  onStreamMessage: message => {
    // We recommend using the server-side message ID as the update key for the same stream message.
    const messageId = message.msgServerId || message.msgLocalId;

    setMessageList(prevMessageList => {
      const msgIndex = prevMessageList.findIndex(
        item => (item.msgServerId || item.msgLocalId) === messageId
      );

      if (msgIndex !== -1) {
        const newMsgList = [...prevMessageList];
        newMsgList[msgIndex] = {
          ...newMsgList[msgIndex],
          // Update the displayed content using the cumulative text merged by the SDK.
          body: message.body,
          // Retain the latest stream metadata.
          stream: message.stream,
        };
        return newMsgList;
      }

      return [...prevMessageList, message];
    });
  },
});
```

After receiving a stream message chunk, you can retrieve its content, transmission state, cumulative merged content, custom type, error code, and optional finish reason. Use the message ID to update the display of the same message.

```typescript
function handleStreamChunk(message: {
  // Server-side message ID. We recommend using it as the unique identifier for the same stream message.
  msgServerId: string;
  // Local message ID. Use it as a fallback if the server-side message ID is unavailable.
  msgLocalId: string;
  body: {
    // Text content in the current message body. For a stream message, this is generally the current cumulative merged content.
    content: string;
  };
  stream: {
    // Incremental text content of the current chunk.
    deltaText: string;
    // Cumulative complete text from the first chunk through the current chunk.
    fullText: string;
    // Current stream message transmission state.
    status: string;
    // Custom stream type, such as `text` or `markdown`.
    customType?: string;
    // Error code. `0` indicates no error, and other values indicate that the stream ended with an error.
    errorType: number;
    // Finish reason code defined by the server according to business semantics.
    finishReason?: number;
  };
}) {
  const messageId = message.msgServerId || message.msgLocalId;
  const stream = message.stream;

  // Current chunk content
  const incrementText = stream.deltaText;

  // Current transmission state
  const status = stream.status;

  // Cumulative merged content
  const fullText = stream.fullText || message.body.content || '';

  // Custom type, such as text / markdown
  const customType = stream.customType;

  // Error code and finish reason
  const errorType = stream.errorType;
  const finishReason = stream.finishReason;

  // We recommend updating the display of the same message by messageId in your app
}
```

## Message content and processing

After receiving a stream message, process it in terms of its current chunk information, cumulative merged content, extension, and transmission state.

### Current chunk information

Retrieve information about the current chunk through `message.stream`.

| Field | Type | Description |
| :--- | :--- | :--- |
| `deltaText` | String | Incremental text content of the current chunk. |
| `status` | StreamMessageStatus | Stream message transmission state corresponding to the current chunk. |
| `customType` | String | Custom stream type defined by your app, such as `"markdown"` to identify the text format. |
| `errorType` | Number | Error code. The default value `0` indicates no error. A value other than `0` indicates that the stream message ended with an error. |
| `finishReason` | Number | Optional. Finish reason code defined by the server according to business semantics. |
| `seq` | Number | Sequence number of the current chunk. |
| `fullText` | String | Cumulative complete text corresponding to the current chunk. |

```typescript
function handleStreamChunk(message: {
  stream: {
    deltaText: string;
    status: string;
  };
}) {
  const stream = message.stream;
  const incrementText = stream.deltaText;
  const status = stream.status;
}
```

:::tip
- `message.stream.deltaText` contains the incremental text of the current chunk.
- `message.stream.fullText` contains the cumulative complete text from the first chunk through the current chunk.
- `message.body.content` is also updated to the current cumulative complete text.
- We recommend displaying the cumulative merged content. For a typewriter effect, you can also use the current chunk content.
:::

### Cumulative merged content

The SDK automatically merges stream message content locally in chunk order and updates the callback message body.

`message.stream.fullText` contains the cumulative merged content from the first chunk through the current chunk. In the current SDK, `message.body.content` also reflects this cumulative result.

```typescript
function handleStreamChunk(message: {
  body: { content: string };
  stream: { fullText: string };
}) {
  const currentFullText = message.stream.fullText || message.body.content || '';
}
```

:::tip
UI recommendations:
- Display the cumulative merged content as the final UI content.
- For character-by-character or segment-by-segment animation, use both the current chunk content and cumulative merged content.
:::

### Extension

Stream messages support the `ext` extension. The SDK exposes the `ext` corresponding to the current chunk in each `onStreamMessage` callback. To save extension information for the complete stream message in your app, place information closely related to the complete message in the first chunk and maintain it by message ID in your app.

:::tip
- We recommend sending extension information closely related to the complete message in the first chunk.
- Do not rely on later chunks dynamically changing `ext` to determine the final business state of the complete message.
:::

### Transmission states and error handling

Retrieve the stream message transmission state corresponding to the current chunk from `message.stream.status`.

The `StreamMessageStatus` enum is described as follows:

| State | Description | Recommended handling |
| :--- | :--- | :--- |
| `STREAM_START` | The first chunk arrives and stream message transmission starts. | Create or locate the corresponding message item, initialize its display, and mark it as generating. |
| `STREAM_IN_PROGRESS` | The stream message is being transmitted. | Continuously refresh the message display with the cumulative merged content and keep the message marked as generating. |
| `STREAM_COMPLETED` | The last chunk arrives and the stream message completes normally. | Display the final merged content, remove the generating state, and handle the message as completed. |
| `STREAM_FULL` | The stream message completes in a single chunk, or a fallback final chunk containing the complete text finishes a transmission with missing chunks. | Display the content directly as a complete message and stop stream rendering. |
| `STREAM_ERROR` | The stream message ends with an error. | Retain the content received so far, stop stream rendering, and display an abnormal termination state or error prompt based on `errorType` and `finishReason`. |

We recommend displaying the cumulative merged content so that users always see the latest complete text. For a stream message that ends with an error, retain the generated content and display a state such as “Interrupted”, “Generation failed”, or “Stopped”, as appropriate for your app.

In this table:

- `errorType === 0` indicates that the current callback does not contain an error state.
- `errorType > 0` indicates that the stream message ended with an error. We recommend logging the error and notifying the user that content generation was interrupted.
- We recommend defining the business semantics of `finishReason` on the server, such as completed normally, stopped manually, timed out, or model error, and mapping them to consistent display text on the client.

## FAQ

#### 1. Can the SDK actively send stream messages?

No. Stream messages [can be sent only through the server-side RESTful API](/document/server-side/message_stream_send_single.html). The Web SDK is responsible only for receiving them.

#### 2. What is the difference between `message.stream.deltaText` and `message.stream.fullText`?

- `message.stream.deltaText`: Content of the current chunk.
- `message.stream.fullText`: Cumulative complete text from the first chunk through the current chunk.

The UI should generally display `message.stream.fullText` or `message.body.content`.

#### 3. How do I determine whether a message has ended?

Check `message.stream.status`. The terminal states are:

- `STREAM_COMPLETED`
- `STREAM_FULL`
- `STREAM_ERROR`

#### 4. Why does `ext` in subsequent chunks not take effect?

Only `ext` in the first chunk is persisted in the final message. Subsequent chunks should not be used to update the final message extension.

#### 5. Do I need to merge chunks myself?

No. The SDK automatically merges the content. However, we recommend updating the UI for the same message by `message.msgServerId` to avoid displaying a single stream message as multiple messages.
